Getting the schema, naming conventions, and relationships right before writing a single controller saves you from painful migrations later. This is also where beginners create the most silent technical debt (missing indexes, no audit columns, inconsistent naming).What to learnNormalization (3NF) and when to deliberately denormalize for read performance.UUID vs auto-increment primary keys.Soft delete vs hard delete.Indexing strategy (B-tree default, GIN for full-text/JSON, composite indexes).Audit columns (created_at, updated_at, created_by, updated_by).Decision: UUID vs Auto-Increment (bigint) Primary KeysUUIDAuto-increment (bigint)ProsSafe to expose in URLs/APIs without leaking record count; can be generated client-side before insert; no collision across environments/shardsSmaller (8 bytes vs 16), faster joins and index scans, human-readable in logsConsLarger index size, random insert order can fragment B-tree indexes (mitigated with UUIDv7), slightly slower joins at scaleLeaks business info (e.g., total number of messes = highest ID), harder to merge data across environmentsRecommendation: Use UUID (v7) for all public-facing entities (mess, review, user, menu_item) because Mess Finder is a public-facing marketplace app — you don't want competitors or curious users scraping sequential IDs to estimate your total mess count or user growth. UUIDv7 (time-ordered) avoids the classic random-UUID index fragmentation problem. Use Postgres's gen_random_uuid() (from pgcrypto) as a baseline, and consider a UUIDv7 generator library once you need index performance at scale (not needed for MVP volume).Naming ConventionsTables: snake_case, plural (messes, menu_items, reviews).Columns: snake_case (created_at, mess_owner_id).Foreign keys: <referenced_table_singular>_id (mess_id, user_id).Join tables: <table_a>_<table_b> alphabetically (mess_favorites).Indexes: idx_<table>_<column(s)> (idx_messes_city_id).Constraints: chk_<table>_<rule>, fk_<table>_<ref_table>, uq_<table>_<column>.Audit Fields (every table)created_at TIMESTAMPTZ NOT NULL DEFAULT now(),updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),created_by UUID NULL,updated_by UUID NULLUse a Hibernate @EntityListeners(AuditingEntityListener.class) + @CreatedDate/@LastModifiedDate (Spring Data JPA Auditing) so you never set these manually.Soft Delete StrategyDecision: Use a deleted_at TIMESTAMPTZ NULL column instead of a boolean is_deleted. A nullable timestamp tells you both whether and when something was deleted — useful for admin audit trails and future "restore within 30 days" features. Apply a Hibernate @SQLRestriction("deleted_at IS NULL") (Hibernate 6.3+, replaces the deprecated @Where) on entities that support soft delete (Mess, Review, MenuItem — not User, which you deactivate
